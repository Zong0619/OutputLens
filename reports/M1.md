## Architecture Impact

### Validated

- **Analyzer Contract (P7)**: A2 implements the contract cleanly -- single responsibility, explicit inputs (`AnalyzerInput("a1", "a1")`), typed output (`list[Claim]` via dict wrapper). Declaration includes id, version, responsibility, inputs, output_type, and layer.
- **Engine-First Separation (P6)**: A2 produces Analysis Model objects (`Claim`). It has no interface awareness. It works identically whether consumed by CLI, API, or browser extension.
- **Explicit Dependency Declaration (P9)**: A2 declares A1 as its sole required input. The orchestrator resolves this correctly.
- **Immutability (P8)**: All `Claim` objects are frozen dataclasses. Position spans are fixed at creation.
- **Text-Anchored Analysis (P11)**: Every claim carries `start_char`/`end_char` in NormalizedText coordinates, projectable to RawInput via PositionIndex.

### Challenged

- **Model Agnosticism (P3) at the implementation level**: A2-001 documents the decision to use deterministic rule-based extraction rather than LLM-based extraction. This preserves model agnosticism -- A2 does not use any AI model to extract claims. However, if future evaluation reveals that a rule-based approach cannot reach >80% F1, the architecture may need to accommodate LLM-assisted extraction while maintaining model agnosticism for the text being analyzed. This tension is documented but not yet resolved.

### No Impact

- **Independent Axes (P13)**: Not tested -- A2 produces claims but does not classify them. Classification axes (Establishedness, Evidence Requirement, Novelty) are downstream.
- **Classification Requires Reasoning (P12)**: Not tested -- no classifications performed.
- **Progressive Analytical Depth (P15)**: Partially tested -- the engine computes claims; interfaces will decide how to render them. No interface exists yet.
- **Composable Analysis (P20)**: Partially tested -- A2 can be requested independently. Full composability validation requires more analyzers.

## Specification Validation

### Requirements Validated

1. **A2 output format (Chapter 12)**: A2 produces `list[Claim]` where each Claim has `id`, `text`, `start_char`, `end_char`, `segment_id`, `claim_type`, `confidence_markers`, and `knowledge_signature`. All fields are populated per spec.
2. **Position preservation (Chapter 12)**: Every claim's position span correctly references offsets in NormalizedText. Regression tests verify round-trip extraction.
3. **Analyzer contract (Chapter 7)**: A2 implements the `Analyzer` abstract base class with `declaration` and `analyze(context)`.
4. **Orchestration integration (Chapter 8)**: A2 executes correctly within the orchestration layer. Dependency on A1 is resolved. Context-based data flow works.
5. **Immutability (Chapter 17)**: `Claim` objects are frozen dataclasses. Post-creation modification raises `FrozenInstanceError`.
6. **AnalysisDocument compatibility (Chapter 26)**: `AnalysisDocument.set_claim()` accepts A2 output. `AnalysisDocument.validate()` verifies claim-level invariants.

### Requirements Difficult to Implement

1. **Claim type classification**: The specification defines 9 claim types. A2-003 documents the decision to default all claims to `factual_assertion`. Full type classification requires linguistic analysis beyond Phase 1 scope. The spec is not violated (it defines types but does not mandate a specific classification mechanism), but a conformant implementation that reads the spec naively might assume claim type classification is required at extraction time. **Recommendation**: The spec should clarify that claim type assignment is progressive -- default types are acceptable; refinement occurs in later phases or via downstream analyzers.

2. **Confidence marker detection**: The specification lists `confidence_markers` as a Claim field. No markers are detected in M1. The field is populated as an empty tuple. **Recommendation**: The spec should clarify that confidence marker detection is optional for claim extraction v0.1 and is a separate analytical concern (arguably part of A5 Evidence Requirement Analyzer or a dedicated analyzer).

### Ambiguities Discovered

1. **Claim boundary definition**: The specification defines a Claim as "a single, self-contained proposition that can be independently evaluated." This definition guided implementation but left significant room for engineering judgment. When is a proposition "self-contained"? When two clauses share a subject, are they one claim or two? The implementation made conservative choices (A2-004 documents specific rules). **Recommendation**: The specification should include boundary examples showing when to split vs. merge, similar to the abbreviation boundary cases documented in A2-004.

2. **A1 output format**: The specification does not define a canonical output structure for A1. The implementation chose `{"normalized_text": NormalizedText, "position_index": PositionIndex}`. This convention (output name matches analyzer_id) is documented in PROJECT_STATE.md but not in the specification. **Recommendation**: The specification should define the canonical output name convention for all analyzers, or explicitly delegate this to implementations.

### Specification Remains Silent On

- Extraction methodology (rule-based vs. ML vs. hybrid)
- Sentence boundary detection algorithms
- Abbreviation handling strategy
- List and enumeration detection
- Claim type defaulting behavior
- Confidence marker detection scope

These are correctly left to implementations per the specification's design principles.

## Known Limitations

### False Positives (Split When Should Not)

- **List continuations**: Coordinating conjunctions where the second clause continues a list rather than forming an independent clause (e.g., "...are generated, interact, or share spatial proximity..."). The heuristic detects "share" as a verb, treating the continuation as an independent clause.
- **Temporal "while"**: The contrastive conjunction splitter may incorrectly split "while" used temporally.

### False Negatives (Not Split When Should)

- **Semicolon-separated clauses**: Independent clauses separated by semicolons without explicit connectors remain as single claims.
- **Colon-separated explanations**: Text like "The reason is simple: data quality matters." remains as one claim.
- **Complex multi-clause sentences**: Implicit clause boundaries without punctuation markers are not detected.

### Deferred to Future Milestones

- **Claim type classification**: All claims are `factual_assertion`. Type refinement is M2+ work.
- **Confidence marker detection**: No hedging/certainty markers extracted. Deferred to M2 or M3.
- **Golden dataset annotation**: GOLD-CLAIM v0.1 not yet created. Deferred to evaluation phase.
- **Evaluation harness**: Not built. Deferred to post-M3.
- **F1 measurement**: No quantitative quality evaluation. Awaiting annotated data.

## Lessons Learned

1. **Punctuation-only text causes infinite loops in sentence splitters**: The `?!\n` input exposed a `punct_pos < start` bug where the lookbehind regex matched already-processed positions. The fix (guard clause) is simple but the failure mode was silent -- 100% CPU, no error. Adding degenerate-input regression tests early prevents this class of bug.

2. **Abbreviation handling is the hardest part of sentence splitting**: The Dr./etc./U.S./approx./Jan. distinctions required three iterations (single list → title/general split → digit-aware general abbreviations). This is inherently a knowledge problem, not an algorithmic one. Future implementations will face the same challenge regardless of methodology.

3. **Conjunction splitting requires clause-level understanding**: The simple `_has_independent_clause` heuristic (verb indicators + minimum word count) works for common cases but produces false positives on list continuations. Full clause analysis requires syntactic parsing, which M1 deliberately avoided.

4. **Position integrity is the most important property**: Every test that verifies `text[claim.start_char:claim.end_char]` matches the claim text is testing the single most important contract -- that claims are traceable to the original text. This is the foundation for inline highlighting, click-to-scroll, and all reader-facing features.

5. **The analyzer contract works as designed**: Wrapping A1 and A2 as `Analyzer` subclasses was straightforward. The contract's constraints (single responsibility, explicit inputs, no consumer awareness) forced clean separation. A2 knows nothing about A3-A16; A1 knows nothing about A2.
